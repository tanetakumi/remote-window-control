# マウス・タッチ入力と相対ポインターモードの調査

調査日: 2026-10-01。対象: 現在の Share App の Web UI、入力プロトコル、Windows 側の入力処理、および Microsoft / W3C の一次資料。

実装方針の確定: この調査後、ユーザーから「完全にスマホ専用」と指定されたため、以下の PC 通常マウス維持案は取り下げた。PC の通常マウス処理は削除し、直接タップと相対ポインターの2モードを実装した。以下の「現在」は実装前の調査時点を指す。実装後の操作方法は README の Input and snapshots を参照。

## 結論

スマホには「相対ポインター（タッチパッド方式）」を追加し、「直接タップ」と切り替えられる構成を推奨する。細かい Windows UI を操作する用途では相対ポインターをスマホの初期設定候補とし、実機で操作速度・精度を確認する。PC の通常マウス操作は現在の座標指定方式を維持する。

相対ポインターでは、指を滑らせてカーソルを移動し、任意の場所をタップして現在のカーソル位置をクリックする。タップはこの方式でも必要になる。「相対マウスかタップか」は、正確には「カーソルを動かしてクリックするか、触れた位置を直接クリックするか」の選択である。

スマホとマウスの両方を使えるようにすることは可能。ただし全入力を相対方式へ変更するだけでは、クリック・ドラッグ・スクロール・表示カーソル・ブラウザーからの解除が揃わない。現在の問題は入力機器が複数あること自体より、機器ごとに意味・状態・スクロール単位が別々になっていることにある。

今回は調査のみ。アプリケーションの実装変更は行っていない。

## 現在の入力経路

`web-ui/src/main.js:289` で同じ video 要素に `attachGestureControls` と `attachMouseControls` を同時に登録している。操作モードを選ぶ UI はない（`web-ui/index.html:80`）。

マウス側は Pointer Events の `pointerType === "mouse"` のみを処理し、タッチ側は Touch Events を処理する。したがってタッチ操作がそのまま二重にマウス操作として送られる構成ではない。既存テストも、タッチから送られるのが `input.tap` 1件だけであることを検証している。

| 操作 | 現在の PC マウス | 現在のタッチ |
| --- | --- | --- |
| ポインター移動 | 映像上のマウス位置を `input.mouseMove` として送る | 通常の1本指移動では送らない |
| 左クリック | 左ボタン down / up | 指を離した位置へ `input.tap` |
| 右クリック | 右ボタン down / up | 450ms の長押しで右ボタン down、指を離すと up |
| 左ドラッグ | 左ボタンを押したまま移動 | 専用ジェスチャーなし |
| 右ドラッグ | 右ボタンを押したまま移動 | 長押し後に移動 |
| スクロール | wheel、現在のマウス位置を対象にする | 12 CSS px 超の1本指移動、または2本指移動。最後にタップした位置を対象にする |
| ピンチ | Ctrl+wheel はリモートに送らない | 距離を測定せず、2本指の中心移動としてスクロール処理する |
| 中ボタン・横ホイール | 中ボタンを処理せず、横 wheel の送信なし | 横 delta を送るが Windows 側が無視する |
| ペン | 専用処理なし | 専用処理なし |

座標は映像内の `x,y = 0..1` に正規化される。余白を除いた映像矩形は `web-ui/src/input/coordinates.js` で計算する。現在はマウスもタッチも最終的には絶対位置を指定する。

入力は `web-ui/src/core/webrtc.js:11,72` の WebRTC control DataChannel を通る。WebSocket はシグナリングを担当する。ホストの `control-server/internal/input/dispatcher.go:91` がコマンドを振り分け、`message_injector.go` が映像座標を対象ウィンドウのクライアント座標へ変換する。

Windows 側は `PostMessage(WM_MOUSEMOVE / WM_*BUTTON*)` と `SendMessage(WM_MOUSEWHEEL)` を使用する。実際の Windows カーソルを動かす入力方式ではない。`input.tap` は mouse move、button down、25ms 待機、button up の短いクリックに変換される。Windows のネイティブタッチを注入しているわけではない。

## コードとイベント再現で確認した問題

### 1. 同じ移動でも、マウスは移動、タッチはスクロールになる

`mouse.js:53` と `gestures.js:96` の動作が異なる。タッチの通常スワイプでは hover 操作もできず、細かいボタンへカーソルを合わせてクリックする手順がない。これは相対ポインターで改善できる。

### 2. タッチには通常の左ドラッグ経路がない

`gestures.js:59` の長押しが押すのは右ボタンである。移動すると右ドラッグになる。文字選択や通常の左ドラッグを行う専用ジェスチャーは実装されていない。長押し右クリック、左ドラッグ、ポインター移動をそれぞれ区別する必要がある。

### 3. スクロールの符号と単位が不一致

再現結果は次のとおり。1本指は判定しきい値を超えてから、追加で20 CSS px 上へ動かした値。

| 入力 | 送信される deltaY | `WheelDelta` による Windows wheel 値 |
| --- | ---: | ---: |
| 1本指を上へ20px | +16 | -1920 |
| 2本指を上へ20px | -20 | +2400 |
| マウス wheel の deltaY = +20px | +0.2 | -24 |

`gestures.js:109` と `:138` で縦方向の符号が逆。タッチの CSS px はほぼそのまま送信されるが、`mouse.js:91` は100pxを1ノッチへ変換する。ホストの `win32/layout.go:32` は全経路を同じノッチ単位として120倍する。

入力値の換算として、20px の1本指操作は20px の wheel 入力の80倍、2本指は絶対値で100倍になる。Windows アプリが実際にスクロールする距離はアプリ側の処理にも依存するため、この倍率は表示上の移動距離を保証するものではない。方式変更とあわせて、方向・単位・細かい入力の累積を統一すべきである。

横方向は `message_injector.go:80` の `Scroll(_, deltaY, ...)` が deltaX を破棄する。タッチが送る横スクロールは実行されない。

### 4. カーソル位置の状態が入力経路間で共有されていない

マウス側の `lastPoint` とタッチ側の `lastTapPoint` は別の状態である。タッチで `(0.1,0.1)` をクリックし、マウスを `(0.9,0.9)` へ移動してからタッチでスクロールしても、送信対象は古い `(0.1,0.1)` のままであることを再現した。

相対ポインター追加時は、現在の論理カーソル位置を共有し、直接タップでもマウス移動でも更新する必要がある。

### 5. 映像余白・キャンセルの取り扱いに差がある

マウスは余白で新しい操作を始めない。タッチは `normalizeClientPoint` の既定の clamp を使うため、上下の余白へのタップが映像端のクリックになった。直接タップモードでは開始点を映像内に限定する方が予測しやすい。

マウスには blur 時のボタン解放がある。タッチは touchcancel と cleanup で解放するが、blur のリスナーはない。イベント再現では長押し中の blur が右ボタンを解放しなかった。実ブラウザーが追加で touchcancel を発生させるかは環境依存であり、全端末で押下が残ると断定はできない。

ホスト側は切断・対象変更時に押下を解放する。モード切り替え・非表示化・Pointer Lock 解除にも同じ解放方針を適用する設計が必要。

### 6. ピンチをズームと区別していない

2本指の距離は計算していない。ピンチしながら中心が5px動くと、deltaY=5 のスクロールを送ることを再現した。中心が動かなければ実質ゼロとなるが、ズーム機能にはならない。映像には `touch-action: none` も設定されている。ローカル映像ズームを追加するなら、2本指スクロールと距離変化の判定を分ける必要がある。

## Microsoft の方式と「相対」の意味

Microsoft の Windows App は、iOS/iPadOS・Android 等で Direct touch と Mouse pointer の2方式を説明している。直接タッチは触れた位置をクリックし、ポインター方式は画面上にカーソルを表示して指の移動で動かす。ポインター方式にはタップで左クリック、ダブルタップ後の保持で左ドラッグ、2本指のタップで右クリック等がある。これは2方式を残す判断の先例になる。ただし、この Web アプリで同じジェスチャーを実装していることを意味しない。[Microsoft: Windows App の入力方式](https://learn.microsoft.com/en-us/windows-app/input-keyboard-mouse-touch-pen)

RDP ActiveX には `RelativeMouseMode` プロパティも存在し、前のマウス位置に対して座標を計算するモードとして説明される。ただし、その設定がスマホの Mouse pointer モードと同じ機能であるとは資料から確認できない。また標準 mstsc の通常 GUI で常に切り替えられるとは断定しない。[Microsoft: RelativeMouseMode](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpclientadvancedsettings6-relativemousemode)

RDP の通常の Mouse Event にはサーバーデスクトップ左上を基準にした xPos/yPos がある。このため、ユーザーから見た相対操作と、通信・ホスト注入が相対デルタであることは分けて考える必要がある。[Microsoft: TS_POINTER_EVENT](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/2c1ced34-340a-46cd-be6e-fc8cab7c3b17)

| 方式 | 実装上の意味 | このプロジェクトへの適用 |
| --- | --- | --- |
| タッチパッド式の相対ポインター | 指の差分を仮想カーソル位置に足す。クリック時にはその位置を使う | 既存の絶対座標コマンドを利用できる。今回の第一候補 |
| PC の Pointer Lock | ブラウザーのマウスを捕捉・非表示にし、連続移動量を取得する | PC 用の追加モード候補。スマホのタッチパッド実装の前提にはしない |
| Windows への相対入力注入 | dx/dy を OS の入力ストリームへ渡す | ホスト入力の設計変更が必要。今回の UX 改善には必須ではない |

Pointer Lock は既存の `setPointerCapture` と異なる。前者はカーソルを隠し画面端を越えた継続的な移動量を扱う。現在の後者は主にドラッグ中のイベント受信先を維持する。Pointer Lock にはユーザー操作による開始と解除手段が必要で、Esc やフォーカス喪失等を扱う。[W3C: Pointer Lock](https://w3c.github.io/pointerlock/)

Win32 の `MOUSEINPUT` は `MOUSEEVENTF_ABSOLUTE` なしで相対移動を指定できる。一方 `SendInput` は HWND を指定して背景ウィンドウだけへ送る API ではなく、OS の入力ストリームへイベントを入れる。採用するなら前景ウィンドウ・実カーソル・ホスト利用者との操作関係を設計する必要がある。Raw Input を使用する対象アプリでの互換性も別途実機検証が必要で、UI を相対化するだけでゲームや3D操作の互換性が得られるとは言えない。[Microsoft: MOUSEINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput)、[Microsoft: SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

## 推奨する UI と実装

タッチ操作に「ポインター / 直接タップ」の明示的な切り替えを設け、選択を保存する。ポインター方式は小さい Windows のボタン・hover・ドラッグを操作しやすい。直接タップは大きいボタンや短い確認操作を素早く行える。指の動きが入力されただけで設定を勝手に切り替えると、同じジェスチャーの意味が変わるため避ける。

| 入力 | 推奨する初期動作 | 選べる別動作 |
| --- | --- | --- |
| PC マウス・物理トラックパッド | 現在の映像座標へのポインティング | 必要な用途で明示的に Pointer Lock |
| スマホの指 | 相対ポインターを初期設定候補として実機評価 | 直接タップ |
| タブレットの指 | 保存設定を優先し、両方式を用意 | 大きい画面で直接タップを初期設定とする案を評価 |
| スマホ・タブレットに接続した物理マウス | mouse イベントを通常のマウスとして扱う | 対応するブラウザーでのみ追加の Pointer Lock |

機器の区別は画面幅や User-Agent だけで固定せず、イベントの `pointerType` を用いる。タッチ方式の設定と物理マウスの処理は分ける。ペン入力の方針も別に決める。

相対ポインターのジェスチャー案は以下。Microsoft の全端末で完全に同一の対応という主張ではなく、このアプリへの設計提案である。

| ジェスチャー | 相対ポインター | 直接タップ |
| --- | --- | --- |
| 1本指でスライド | ボタンを押さずカーソル移動 | 従来の1本指スクロールを残す案 |
| 短いタップ | 現在のカーソル位置を左クリック | 触れた位置を左クリック |
| ダブルタップ後、2回目を保持して移動 | 左ボタンを押してドラッグ | 触れた位置から左ドラッグ |
| 長押しまたは2本指タップ | 右クリック。通常のカーソル移動と判定を分ける | 触れた位置を右クリック |
| 2本指でスライド | 現在のカーソル位置でスクロール | 現在の論理位置を使う等、対象を明確に決める |

最初の実装は次の順序が適切。

1. スクロール方向・単位を統一し、タッチの終了・キャンセル・余白判定を整理する。
2. 論理カーソル位置と押下状態を管理する共通コントローラーを設ける。マウスとタッチの入力元は保持し、同時入力時の所有権を定める。
3. 映像矩形に対応した仮想カーソルを追加する。初期位置は中央とし、直接クリック・マウス移動でも位置を更新する。
4. 指の差分をカーソル位置へ加算する。指を離して置き直す際には座標を飛ばさない。感度・映像倍率・CSS px とホストの DPI の関係を定義する。
5. `input.mouseMove / mouseDown / mouseUp / tap / scroll` の既存コマンドへ変換し、タッチ方式の切り替えと保存を追加する。
6. 対象変更時には押下とカーソルを初期化する。リサイズ時には正規化位置を維持する等、映像変更との整合を決める。
7. PC で相対マウスを使う必要が確認された場合に Pointer Lock を追加する。開始操作を誤クリックとしてホストに送らず、解除・失敗・非対応時を扱う。

仮想カーソルは Windows の実カーソルとは独立している。現在の入力方式では物理カーソルが動かないため、スマホで相対ポインターを使うには UI が論理位置を表示する必要がある。ホスト側カーソル画像の映像への混入・二重表示と、I-beam 等のカーソル形状取得は実機確認項目とする。

フロント側で絶対位置へ変換すれば最初の段階で相対コマンドを新設する必要はない。移動の送信をまとめる場合、絶対位置は最新位置を送ればよいが、相対デルタを採用する場合は途中の差分を捨てずに加算する。クリック前に最新位置を確定し、down/up の順序を維持する。

## 検証範囲と未確認事項

- 既存 Web UI テスト: `cd web-ui && npm test`、21件成功。
- 調査用の一時イベント再現: 8項目成功。1本指/2本指の符号、wheel 換算差、古い tap 位置、長押し右ドラッグと blur、余白タップ、ピンチ中心移動、pen の専用処理不在を確認した。ソースやテストファイルは変更していない。
- 実行環境の Node は v22.22.1。package.json の要求は Node >=24.21.0 <25 なので、指定されたバージョンでの検証ではない。
- Go の入力・座標テストは実行を試みたが、環境に Go がなく実行できなかった。
- Windows の実ウィンドウ、実機 iPhone/Android、映像カーソルの表示、対象アプリごとの入力互換性、実ネットワーク遅延は未検証。
