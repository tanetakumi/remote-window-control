# 画面転送の通信量削減計画

作成日: 2026-10-01  
更新日: 2026-10-01（段階3のVP8送信抑制とカーソル非表示を、実機確認を経て固定の仕様として採用）  
状態: 段階1は実装と実機計測を完了。段階3のVP8送信抑制（ハートビートあり）は実機で成功を確認し、設定による切り替えをなくして唯一の動作とした。ホストのカーソルは常にキャプチャしない。

## 目的と推奨方針

Windowsの選択ウィンドウをスマホのブラウザから操作する機能を維持し、画面転送の通信量を減らす。文字の読みやすさ、操作への追従、接続と映像の復旧も評価する。

次の順序で進める。

1. Windows SDK参照を26100系へ更新し、WGCの`DirtyRegions`を`ReportOnly`で取得・計測する。既存の全画面取得とVP8配信を比較基準にする。
2. 測定結果に応じて、静止中のVP8送信抑制、または文字・UI用途の矩形／タイル転送とCanvas表示のどちらへ進むかを決める。
3. 選んだ方式に必要な分だけ、変更情報をGoへ渡す処理を作る。VP8の送信抑制なら「前回の符号化以降に変化があったか」で足りる。未送信の変更矩形の累積が必要なのは矩形／タイル転送の場合に限る。
4. 必要性が確認できた場合に、`ReportAndRender`と部分コピー、スクロール最適化、動画との切り替えを追加する。

初期導入の対象は、変更矩形を取得して件数・面積・更新頻度を把握するところまでとする。変更情報の取得だけではネットワーク通信量は減らない。送信方式の変更は、実際のアプリケーションで変更領域がどれほど小さくなるかを確認してから判断する。

RDPの変更領域送信、キャッシュ、内容に応じた圧縮という考え方を取り入れる。RDPプロトコル全体の再実装や、リモートデスクトップ基盤への置き換えは初期段階の対象に含めない。

既存の10fps・品質設定は比較の基準として残し、Windowsとスマホでの測定を根拠に既定値の変更を判断する。VP8の設定調整は測定後の選択肢とし、DirtyRegionsの評価より先に実施する前提にはしない。矩形／タイル差分の大幅な削減効果は、静止画面や局所的に更新される画面を対象とした仮説であり、実機での削減率は未確認。

## 現行構成と確認できた課題

```text
Windows Graphics Capture
  → CaptureProbeで全画面BGRAを取得
  → ホスト内のパイプでGoへ渡す
  → FFmpegでVP8に符号化
  → Pion WebRTCで送信
  → ブラウザのvideo要素で表示
```

VP8はフレーム間圧縮を使用している。外部ネットワークへ全画面BGRAを毎回そのまま送信しているわけではない。

| 項目 | 作成時点の状態 | 評価する影響 |
| --- | --- | --- |
| 符号化設定 | 10fps、ビットレート目標6Mbps、CRF 10、realtime | 品質と通信量の関係 |
| キーフレーム | 最大間隔20フレーム。10fpsで約2秒 | 静止中も全体更新に相当するデータが定期的に発生 |
| 静止中 | 新しいキャプチャがなくても最新画像を再符号化 | 無変化時の継続的な送信とCPU負荷 |
| キャプチャ | GPUから全体をコピーしてCPUへ読み出す | ローカルのコピー、メモリ、プロセス間通信の負荷 |
| WGC変更情報 | 段階1で26100系SDKへ更新し、計測時のみReportOnlyで取得 | 実機での矩形の大きさ・頻度・画素変化との一致 |
| WGCのフレーム到着 | 静止中のウィンドウではFrameArrivedが発生しない。Goは最新画像を再符号化し続ける | 静止の検出自体はDirtyRegionsなしでも可能 |
| カーソル | `IsCursorCaptureEnabled`は既定の有効。ブラウザは独自のカーソル表示を重ねている | ホストのカーソル移動によるフレームと変更矩形の発生 |
| フレーム受け渡し | 古い未処理フレームを捨てて最新だけを保持 | 差分化すると途中の変更を取りこぼす可能性 |
| RTCP | 既定のインターセプター（NACK等）は登録済みで、読み取りで動作させる。アプリ側はPLI/FIRを破棄 | 外部FFmpeg（CLI）へは実行中にキーフレームを要求する手段がない |
| 帯域適応 | 外部FFmpegの設定へ帯域推定結果を反映する処理はない | 低速回線での送信量と遅延 |
| 解像度 | 表示領域にdevicePixelRatioを掛けてウィンドウサイズを要求 | 高密度画面でキャプチャ画素数が増える可能性 |
| クライアント計測 | getStatsの映像受信バイト数からkbps表示を算出 | 端末全体の通信量との差 |

`-b:v 6M`はビットレート目標であり、常時6Mbpsを送る指定でも、瞬間的な通信量の厳密な上限でもない。CRFとの組み合わせや画面内容によって出力が変わる。

例えば表示領域390×800、devicePixelRatio 3なら、1170×2400のクライアント領域を要求する。実サイズはモニターの作業領域などで制限されるため、要求値と実際のキャプチャ解像度を両方記録する。画素数の増加率と通信量の増加率は同一ではない。

1920×1080のBGRAを10fpsで渡すと、画素データは約83MB/sになる。これはホスト内の転送量であり、ネットワーク通信量とは別に測定する。

## 方式の比較

以下の効果と導入規模は、現行構成に対する設計上の評価。

| 方式 | 適した用途 | 利点 | 主な制約・導入規模 |
| --- | --- | --- | --- |
| WGC DirtyRegionsの取得・計測 | 差分転送の適合性調査 | Windowsが報告する変更矩形を使って判断できる | 取得だけでは通信量は減らない。小 |
| 現行VP8の調整 | 幅広い用途 | 既存のブラウザ表示を活かせる | 静止中の送信削減には時刻と復旧の設計も必要。小〜中 |
| タイル／矩形差分を画像として送信 | エディタ、ターミナル、設定画面 | 無変化時に画面データ送信を停止できる。文字を可逆圧縮できる | 状態同期、送信制御、Canvas表示が必要。中〜大 |
| 差分画像と動画の切り替え | UIと動画が混在する画面 | 用途に応じて方式を選べる | 切り替え時の同期と判定が複雑。大 |
| H.264、VP9、AV1への変更 | 動きの多い画面 | 圧縮効率やハードウェア処理の改善候補 | 端末とWebRTCでの対応、CPU、画質を測定。中〜大 |
| noVNC／Guacamoleの利用 | 既存のリモート画面基盤の利用 | 既存プロトコルとクライアントを活用できる | サーバーや接続構成の変更が必要。大 |

初期の差分方式はWGCによるウィンドウ取得を維持する。Desktop Duplication APIには変更矩形と移動矩形があるが、デスクトップ画面取得を対象とするため、選択ウィンドウ共有への適合性を別途評価する必要がある。

## 調査時の参考実験

合成した1920×1080の文字画面を、LinuxのFFmpeg 8.0.1で各12秒間符号化した。現行相当の設定からキーフレーム最大間隔だけを20フレームと100フレームに変更して比較した。

共通設定はBGRA入力、10fps、yuv420p、libvpx、ビットレート目標6Mbps、CRF 10、deadline realtime、cpu-used 4、auto-alt-ref 0。初回キーフレームを含む平均で、符号化したVP8ペイロードのみを集計した。

| 合成画面 | 20フレーム間隔（約2秒） | 100フレーム間隔（約10秒） | ペイロード減少率 |
| --- | --- | --- | --- |
| 完全な静止画面 | 1,348.76kbps | 549.60kbps | 59.3% |
| 文字カーソルの点滅 | 1,352.58kbps | 568.20kbps | 58.0% |
| スクロール | 1,860.72kbps | 1,060.15kbps | 43.0% |

静止画面の20フレーム間隔設定では、ペイロードの約64.6%をキーフレームが占めた。DirtyRegionsの計測と併せて定期キーフレームの影響を調べる参考となる。この結果を理由に、DirtyRegions導入前のVP8設定変更を必須にはしない。

これはWindowsでの実キャプチャ、WebRTC通信、スマホでの表示を測定した結果ではない。通信ヘッダー、再送、画質の同等性、損失後の復旧時間は評価していない。10秒間隔の採用や、本番で同じ削減率が得られることを示す結果ではない。

## 段階的な実施計画

### 段階1: SDK更新とReportOnlyでの変更矩形計測

- コンパイル時のWindows SDK参照を26100系へ更新する。最低対応OSは別の設定として明示し、API非対応環境では従来のWGC取得を使う。
- NuGetのロックファイル、CaptureProbeの開発用探索パス、そのテスト、CIとREADMEのビルド出力パスを更新する。
- `ApiInformation.IsPropertyPresent`などで`DirtyRegionMode`と`DirtyRegions`のAPI有無を確認する。Windowsのビルド番号だけに依存した分岐にしない。
- 対応環境では`ReportOnly`を使用し、フレームを破棄する前に変更矩形を取得する。矩形情報を画像・解像度・フレーム番号と対応づけて保持する。
- 既存の全画面コピーとVP8配信を使い、変更矩形の件数、重複を除いた面積比、全画面更新の割合、無更新の頻度を集計する。
- 静止、文字入力、カーソル点滅、縦横スクロール、写真、動画について、変更矩形と実際の画素変化の対応を確認する。
- 初回、リサイズ、API非対応、変更情報が取得できない状態を、単純に「変化なし」と扱わない。
- 比較には実キャプチャ解像度、端末、ブラウザ、回線条件、アプリケーションを記録する。現行VP8のペイロード、キーフレーム、受信量、ネットワーク全体の通信量も測定する。
- 正常な静止状態とキャプチャ停止を区別できる計測項目を設ける。計測出力は集計してstderrやホストログへ出し、画素転送用stdoutへ混入させない。

完了条件: API対応・非対応環境で従来の表示を維持でき、実アプリでの変更矩形の大きさと更新頻度が分かる。キャプチャと送信の負荷を分けて評価し、次段階へ進む用途を選定できる。この段階に通信量削減の達成は要求しない。

#### 段階1の実装内容（2026-10-01）

- CaptureProbeのTFMを`net10.0-windows10.0.26100.0`へ変更し、`SupportedOSPlatformVersion`を`10.0.19041.0`とした。参照パッケージは`Microsoft.Windows.SDK.NET.Ref 10.0.26100.57`。ロックファイルの差分はTFMのキーだけで、CsWinRT 2.3.1のまま変更していない。
- CsWinRTの投影には対応OSの属性がなく、26100専用APIを判定なしで呼んでもCA1416の警告は出ない（確認済み）。API判定の漏れは、24H2より前の実機で確認する必要がある。
- `SHARE_APP_CAPTURE_STATS`（`off`／`on`／`verify`、環境変数または`.env`）で計測を有効にする。既定の`off`では、DirtyRegionModeの設定と矩形の取得を一切行わず、従来どおりに動作する。
  - CaptureProbeは`--stats`または`--stats-verify`を受け取り、WGCフレームごとに集計して、5秒ごとに`[capture-stats]`行をstderrへ出力する。stderrの内容はホストログへ記録される。フレームが届かない区間でも行を出力するため、正常な静止とキャプチャ停止を区別できる。
  - 集計はC#の`ProcessFrame`で行う。`StreamFrames`による最新フレームへの集約より前のため、Goへ渡らなかったフレームも数える。`streamed`はGoへ渡したフレーム数。
  - 初回、リサイズ直後、API非対応、取得失敗のフレームは`unknown`として数え、`empty`（空の矩形一覧）とは区別する。
  - 面積は重複を除いた和集合で数え、`empty`／`le1`／`le10`／`le50`／`lt100`／`full`（%）に分類する。
  - `verify`では直前のWGCフレームと画素単位で比較し、矩形の外で変化した画素（`missed_px`）と、画素が変化しなかったフレーム（`unchanged`）を数える。比較は`_frameLock`の中で全画面を走査するためCPU負荷が高い。基準測定には使わない。
  - Goは5秒ごとに`media stats`行を出力する。内容は、新しいキャプチャフレーム数、符号化した入力フレーム数、VP8サンプル数・バイト数・kbps、キーフレーム数・バイト数。値は符号化ペイロードだけで、RTPや再送は含まない。終了時の`capture stopped`行には、計測の設定にかかわらず累計を出力する。
- `SHARE_APP_CAPTURE_CURSOR=off`（CaptureProbeの`--no-cursor`）で、ホストのカーソルをキャプチャ画像から除く。計測で比べるための設定であり、既定は従来どおり`on`。

#### 段階1の結果に基づく判断

- 静止中のフレーム到着の有無はDirtyRegionsがなくても分かる。DirtyRegionsで新しく分かるのは、変化のないフレーム（`empty`。カーソルなど）の判別と、変更面積の分布。
- VP8の送信抑制を選ぶ場合、PLI/FIRへの対応（段階3）が実現できるかで可否が決まる。外部FFmpegでの対応方法を最初に調べる。

#### 段階1の初回実機計測（2026-10-01、`verify`、カーソル`on`）

| 対象 | 計測時間 | VP8平均 | 取り込んだフレーム → VP8サンプル |
| --- | --- | --- | --- |
| ChatGPT | 20.6秒 | 613kbps | 63 → 191 |
| Explorer | 12.1秒 | 313kbps | 2 → 105 |
| Chrome | 16.8秒 | 570kbps | 52 → 152 |
| 合計（時間加重） | 49.4秒 | 約525kbps | 117 → 448 |

- kbpsはVP8ペイロードのみで、RTPなどのオーバーヘッドは含まない。
- Explorerでは新しいフレーム2枚に対してVP8サンプルが105個送られた。約471KBのうち約408KBがキーフレームだった。静止中の再符号化と定期キーフレームが、通信量の大半を占めている。
- 画素比較ができた209枚で`missed_frames=0`、`missed_px=0`。うち77枚は画素の変化がなかった。Explorerの区間は`verified=0`のため、この検証には含まれない。
- カーソル`off`だった過去のChrome計測は約423kbpsだったが、対象画面と操作が揃っていないため、カーソルの効果とは判断しない。
- 判断: 矩形／タイル転送より先に、新しい画面がない間のVP8再符号化を止める方式（段階3のVP8維持）を試作する。変化のないフレームが多いため、Go側の画素比較で「変化なし」を判定する。段階2の矩形の受け渡しは行わない。

### 段階2: 変更情報の受け渡しと累積（段階3で選んだ方式に応じて実施）

段階1の計測を終えて段階3の方式を決めてから着手する。VP8の送信抑制を選んだ場合は、フレームごとの「変化あり／なし／不明」の受け渡しだけを作り、以下の矩形の累積は行わない。以下の項目は矩形／タイル転送を選んだ場合の内容。

- CaptureProbeとshare-hostは同じZIPで配布するため、拡張した形式は帯域内でバージョンを交渉するのではなく、新しいCLIモード（`--stream-v2`など）で切り替える。古いCaptureProbeは未知の引数に対してusageを表示して終了するので、判別できる。
- CaptureProbeからGoへ、完全な最新画像と、それに対応する変更情報を渡す形式を設計する。
- 現在の24バイトBGRAヘッダーには矩形情報がないため、プロトコルを明示的にバージョン化する。API非対応・変更情報不明・全体更新を区別できるようにする。
- C#では、Goへの受け渡しまでに発生した変更領域を累積する。画像と変更情報の取得・累積解除を同じ同期単位で行い、同時に到着した更新を消さない。
- Goでは、古い未処理フレームを置き換える際に必要な変更情報を最新フレームへ引き継ぐ。同じ世代の矩形をまとめ、保持量に上限を設ける。上限を超えた場合は全体更新へまとめる。
- 画像の取得、Goへの受け渡し、ブラウザへの送信、ブラウザでの適用を別の進行状態として扱う。受け渡し完了をブラウザ表示完了と同一視しない。
- 初回、リサイズ、対象変更では画像の世代と変更累積を切り替え、全体更新を要求する。
- 矩形の境界、個数、データサイズを検証し、変更領域の集約にかかる時間とメモリを測定する。

完了条件: C#とGoの両方で途中フレームを破棄しても、送信に必要な変更情報が欠けない。画像と矩形の対応、初回・リサイズ・対象変更時の全体更新を検証できる。この段階でも送信は現行VP8を基準とする。

### 段階3: 測定に基づく通信量削減

段階1の結果から、次の優先順位を判断する。静止時間が長い用途はVP8の無変化時送信抑制、局所的な更新が多い文字・UI用途は矩形／タイル転送を候補にする。VP8の調整をすべて終えることを、矩形転送の前提条件にはしない。

#### VP8を維持する場合

- DirtyRegionsと必要に応じた画素比較を使い、無変化時の更新頻度を下げる、または送信を抑制する。
- PLI/FIRをエンコーダーのキーフレーム生成へ接続し、要求の集約と頻度制限を設ける。送信抑制とキーフレーム間隔延長の前に復旧を検証する。外部FFmpeg（CLI・パイプ入力）は、実行中の任意の時点でキーフレームを要求する手段を持たない（`-force_key_frames`は事前に決めた時刻に対する指定）。候補は、要求時のエンコーダー再起動（遅延と再起動回数を測定）と、libvpxを直接扱う構成への変更。この方法が決まるまで、VP8の送信抑制とキーフレーム間隔の延長は採用しない。
- 固定フレーム間隔を前提とする現在のIVF処理とRTPタイムスタンプを、可変更新に合わせて設計する。
- キーフレーム最大間隔、品質・ビットレート目標、解像度、画面内容向け設定は、必要性を測定して個別に比較する。
- 単に入力を止める変更や、参照関係を考慮せずに符号化済みフレームを捨てる変更は採用しない。
- 頻繁なFFmpeg再起動はキーフレーム増加につながるため、調整や復旧による再起動回数も測定する。

##### 試作の実装内容（2026-10-01）

- `SHARE_APP_IDLE_ENCODING=pause`で有効にする。既定の`continuous`は従来どおり、最新画像を10fpsで再符号化し続ける。比較と切り戻しのため、既定値は実機検証まで変更しない。FFmpegの引数は変更していない。
- `pause`では、新しいフレームのサイズと画素が直前の画像と同じ場合を「変化なし」として扱う。比較はGoで全画素を`bytes.Equal`で行う。変化があると、その後1秒間（10フレーム）は同じ画像の符号化を続けて画質を整え、その後は1秒に1回の符号化（ハートビート）に落とす。`pause`では定期キーフレームをなくす（`-g 1000000`）。キーフレームは、エンコーダーの開始時と、PLI/FIRに応じた再起動時だけに出る。
- 入力を止めても、FFmpeg 8.0.1（libvpx、realtime）は直前に入力したフレームを13〜48msで出力することを確認した。次の入力を待ってフレームが溜まることはない。
- PLI/FIRへの応答: RTCPを解析し、PLIまたはFIRを受けたらパイプラインへキーフレームを要求する。要求より後にキーフレームが送られていれば、それで応答済みとする。そうでなければエンコーダーを再起動し、最初のフレームをキーフレームにする。再起動はエンコーダーの開始から1秒以上たっている場合に限る。この応答は`continuous`でも有効。
- RTPタイムスタンプ: 送信が止まっていた時間ぶんを、空のサンプルで進める（Pionはパケットを送らずにタイムスタンプだけを進める）。符号化を止めた区間、エンコーダーの再起動、対象ウィンドウの変更をまたいでも、RTPの時刻が実時間に沿う。
- 確認方法: Goのテストで、次の点を確認した。
  - 静止画面では1秒分（約10サンプル）を送った後、1秒に1回の差分フレーム（キーフレームではない）だけになる。
  - `pause`では、20フレームを超えて符号化しても、キーフレームは最初の1枚だけになる。
  - 画素の変化がない新フレームでは再開しない。
  - 変化が続く間は符号化を続ける。
  - 停止中のキーフレーム要求に対して、ffmpegで復号できるキーフレームを送る。
  - テスト用のPionブラウザからのPLIで、停止中の映像にキーフレームが届く。そのときのRTPタイムスタンプの間隔が実時間と一致する。
  - PLIの配線またはタイムスタンプ補正を外すと、テストが失敗する。
- `media stats`と`capture stopped`の行に`forced_keyframes`（要求によって再起動した回数）を追加した。

##### 初回試作の実機結果とハートビートの追加（2026-10-01）

最初の試作では、静止中に符号化を完全に止めていた。

- 静止中の再符号化は止まった。Explorerでは約34秒で取り込みフレームが2枚だった。
- しかし`forced_keyframes`が9回発生した。合計約652KB、平均約155kbpsで、送信量の大半がキーフレームだった。
- Chromeでカーソルを`off`にした計測（約28秒）でも、`forced_keyframes=6`、約552KBのうち約544KBがキーフレームだった。

原因はlibwebrtcの受信処理にある（`video/video_receive_stream2.cc`の`OnDecodableFrameTimeout`）。

- 復号できるフレームが`kMaxWaitForFrame`（既定3秒）届かず、最後のパケットから5秒以内であれば、受信側はキーフレームを要求する。
- 要求に応えて送るキーフレームが「最近のパケット」になるため、約3秒＋エンコーダー再起動時間ごとに要求と応答が繰り返された。計測された約3.8秒間隔と一致する。

対策として、静止中も1秒ごとに最新画像を1枚符号化する。ローカルで1080pの合成文字画面を測った結果は次のとおり。

- 静止中の差分フレームは約200〜300バイト（1秒に1回なら約2kbps）。
- キーフレームは約292KB。
- 従来の`-g 20`のまま1秒ごとに符号化すると、20秒ごとに約223KBのキーフレームと、画質を戻すための約95KBの差分が発生する。そのため`pause`では定期キーフレームもなくした。

パケット損失からの復旧は、NACKによる再送と、PLI/FIRに応じたエンコーダー再起動で行う。

##### 採用（2026-10-01）

ハートビート版を実機で確認した。静止時の通信量が大幅に減り、表示と操作にも問題はなかった。この結果を受けて、次のとおり固定の仕様にした。

- `SHARE_APP_IDLE_ENCODING`と従来の`continuous`動作を削除した。変化後1秒は10fps、その後は1秒ごとのハートビートで送る動作だけになった。ffmpegの`-g`は`1000000`に固定した。
- `SHARE_APP_CAPTURE_CURSOR`と、CaptureProbeの`--no-cursor`を削除した。ストリームでもスナップショットでも、ホストのカーソルを常にキャプチャしない。ブラウザ側は独自のカーソル表示を重ねている。
- 削除した2つのキーが`.env`に残っていると、起動時に行番号付きのエラーになる。
- 従来の動作へ戻すには、Gitの履歴を使う。
- 以下は試作時点の確認項目。採用後も、損失のある回線での`forced_keyframes`の回数と復旧時間は、引き続き観察する。

##### 実機で確認すること

- 同じ対象と操作で`continuous`と`pause`を比べ、通信量（VP8と端末側）を測る。
- iPhoneのSafariで、長時間映像が届かない状態でも表示が維持されること、再開後に遅延なく描画されること。
- スクロールや文字入力の直後に、1秒間の符号化で文字の画質が十分に回復すること。
- 帯域制限やパケット損失のある回線で、`forced_keyframes`の回数と映像の復旧時間。

#### 矩形／タイル転送へ進む場合

初期構成は次のとおり。

```text
WGCをReportOnlyで取得
  → 完全な最新画面と累積したDirtyRegionsを保持
  → 変更矩形または変更タイルを抽出
     （必要に応じて矩形内の画素を送信基準の画像と比較）
  → 必要に応じて隣接タイルを矩形へまとめる
  → PNG／可逆WebPで圧縮
  → 画面用DataChannelで送信
  → ブラウザで更新順序を維持してCanvasへ反映
```

- 初回に全画面を送信し、その後は変更領域を送る。
- DirtyRegionsの矩形を使う方式と、矩形をタイルへ展開する方式を比較する。タイルサイズは64×64と128×128などを比較し、圧縮効率と集約・描画負荷で選ぶ。
- 最初は文字とUIを可逆圧縮する。写真への非可逆圧縮の導入は画質評価後に判断する。
- 画面用DataChannelは入力用の`control`と分ける。初期方式は信頼性と順序を保証する送信を使用する。
- 画像データはバイナリで扱い、メッセージサイズに応じて分割する。
- Canvas用の接続準備完了判定、入力座標変換、ビットレート表示を用意する。
- 差分非対応のクライアントや失敗時には、現行VP8へ戻せるようにする。

対応環境ではDirtyRegionsを変更候補の抽出に使う。API非対応環境や情報が不明な場合は全体更新または画素比較へ戻す。DirtyRegionsが広い範囲を示す場合には、その矩形内の画素比較で送信領域を絞る効果を評価する。

完了条件: 同じ用途・回線条件で通信量削減を確認し、可読性、操作遅延、復旧時間の許容範囲を満たす。矩形転送では、全画面同期後の完全な静止状態で画面画像を継続送信しないこと、フレーム破棄・低速回線・リサイズ後も正しく表示されることを確認する。接続維持や統計メッセージは別途通信量に含める。

### 段階4: 必要に応じた追加最適化

- `ReportAndRender`と矩形単位のGPU／CPUコピーを評価する。完全な画面の保持、初期化、リサイズ時の再同期を先に設計する。
- 現在のVortice.Direct3D11にある`CopySubresourceRegion`を利用する候補を評価し、矩形数が多い場合の負荷も比較する。コピー削減によるCPU・GPU・ローカル転送量の改善と、ネットワーク通信量の削減は分けて測定する。
- スクロール時に既存の表示領域を移動し、新しく露出した部分だけを送る。移動量の検出とコピー元の整合性を確認する。
- 変更率、予測送信量、描画遅延を使って、差分画像と動画を切り替える。
- 切り替え判定には一定の継続条件を設け、短時間で方式が往復しないようにする。
- 初期の切り替え単位は画面全体とする。複数の動画領域と差分画像を同時に合成する構成は後段で評価する。
- 必要ならH.264などのハードウェア符号化、VP9、AV1を実機で比較する。CPU負荷低減と通信量削減を別々に評価する。
- Pionの帯域推定を送信量制御へ接続する。外部FFmpegでの設定反映方法と、再起動による影響も評価する。

完了条件: 段階3で確認した弱点に対して改善が得られ、追加の複雑さに見合う効果がある。

## 差分方式の必須設計

### WGCの変更領域と互換性

WGCには`Direct3D11CaptureFrame.DirtyRegions`と`GraphicsCaptureSession.DirtyRegionMode`がある。26100系のWindows SDKを参照し、実行時にAPIの存在を確認する。現在のSDK対象は`net10.0-windows10.0.19041.0`で、ローカルの19041系参照アセンブリにはこれらのAPI定義がないことを確認済み。

コンパイル対象は`net10.0-windows10.0.26100.0`を候補にする。最低対応OSは`SupportedOSPlatformVersion`などで別途指定し、既存の対応範囲を維持する。SDK参照の更新と実行時のAPI対応は別に検証する。

- `ReportOnly`: 全体画像を取得しながら変更領域を参照する。初期導入はこのモードを使用する。
- `ReportAndRender`: 変更領域内の画素だけが有効。前回の完全な画面へ合成する処理が必要。段階4の追加最適化として評価する。
- API非対応時: 通常のWGC取得と画素比較へフォールバックする。
- 初回、リサイズ、API非対応、情報取得失敗では変更領域不明または全体更新として扱い、空の矩形一覧による無変化判定と区別する。
- 変更領域が実アプリでどれほど小さくなるかを測定する。変更情報を得るだけではネットワーク通信量は減らない。

`ReportAndRender`を使用する場合は、有効な更新を完全な画面へ反映してからフレームを破棄できる構造にする。現在の全画面コピー処理をそのまま使用しない。

### フレーム破棄と送信基準

現在のキャプチャ側は最新画像を取り出し、Go側も古い未処理フレームを捨てる。最新フレームに付随する変更領域だけを送ると、捨てたフレームで発生した変更が欠落する。

例えばフレームAで左側、Bで右側が変わり、Aを破棄した場合、Bの変更領域だけでは左側を更新できない。

- 初期設計は`ReportOnly`の完全な最新画像を保持し、未送信の変更領域を累積する。C#からGoへの受け渡し前と、Goでのフレーム破棄の両方に対応する。
- 同じ世代の矩形を累積し、画像と対応づける。サイズや対象が異なる世代を混ぜない。必要に応じて送信基準の画面と画素比較する。
- 比較基準は単純な「直前にキャプチャした画面」にしない。
- 送信・受信・描画のどの完了を基準にするかを明文化する。初期設計は更新バッチの適用確認を基準とする案を評価する。
- 初期の画像パッチは対象領域を置き換える形式とし、XORなど基準画像に強く依存する形式は後段で評価する。
- ハッシュを使用する場合は、衝突による更新欠落への対策を定める。

### 同期と復旧

- 初回、再接続、リサイズ、対象ウィンドウ変更、表示方式の変更で全体同期する。
- 画面の世代番号、更新番号、解像度、座標、圧縮形式をプロトコルに含める。
- 分割メッセージの欠落・中断と、画像デコード失敗を検出できるようにする。
- 古い世代や更新の画像を適用しない。非同期の画像デコードが完了した順に無条件で描画しない。
- 一つの更新バッチの適用単位を定め、途中状態の表示や完了通知の扱いを設計する。
- 同期不一致やデコード失敗時には全体同期を要求する。
- 定期的な全画面送信の必要性は検証で判断する。初期設計はイベントに応じた全体同期と小さな状態確認を基本とする。

### 低速回線と送信待ち

- 送信待ちのバイト数、更新数、経過時間に上限を設ける。
- 未送信の同じタイルは最新内容へまとめる。必要な変更領域の情報は残す。
- 送信済みデータは取り消せるものとして扱わない。
- 入力用と画面用のチャネルを分けても同じ回線を共有する。画面送信が入力遅延を増やさないように送信量を調整する。
- 交渉された`maxMessageSize`に合わせて分割し、過大な一括送信を避ける。
- 切断、対象変更、終了時に送信とデコード処理を止め、古い画像を適用しない。

### 表示と既存機能

現在のブラウザ実装はvideo要素と映像フレームの到着を接続準備完了判定に使う。Canvas方式では、全体同期の適用と入力チャネルの準備を使う判定を追加する。

タップ、マウス、ドラッグ、スクロール、文字入力、貼り付け、日本語IME、画面回転、フルスクリーンの動作を維持する。映像とCanvasで同じ正規化座標を使える表示抽象を設計し、余白、拡大縮小、DPI、リサイズ後の入力位置を検証する。

## 検証項目と採用判断

実機測定は同じアプリ、画面サイズ、操作手順、回線条件で行い、初回同期と定常状態を分ける。静止画面などは12秒の参考実験より長い測定区間を用意し、複数回の結果を比較する。

| シナリオ | 確認すること |
| --- | --- |
| 初回接続 | 全体同期の時間、最初の表示、入力可能になる時点 |
| 完全な静止画面 | 定常時の画像送信量、CPU、スマホの描画・デコード負荷 |
| 文字入力とカーソル点滅 | 小領域の更新、細い文字と色付き文字の可読性、操作遅延 |
| 縦横スクロール | 通信量、表示の正しさ、追従、コピー最適化の効果 |
| 写真と動画 | 差分方式が不利になる条件、画質、動画方式との比較 |
| リサイズ、DPR変更、画面回転 | 世代切り替え、全体同期、入力座標の整合性 |
| 回線遅延、帯域制限、パケット損失 | 入力遅延、送信待ち上限、復旧時間 |
| フレーム破棄、画像デコードの順序逆転 | 更新の欠落や古い画像の上書きが起きないこと |
| 再接続、対象変更、ページの背景化 | 古い更新の排除、停止処理、再同期 |
| WGC変更APIの対応／非対応環境 | API判定、通常取得へのフォールバック |
| カーソルの取り込みの有無 | ホストのカーソル移動によるフレーム・変更矩形・符号化量の違い |
| 初回・リサイズ・変更情報不明 | 空の矩形一覧を理由に必要な全体更新を省略しないこと |
| C#からGoへの受け渡し中のフレーム到着 | 画像と矩形が一致し、累積解除で新しい変更を消さないこと |

収集する指標:

- 符号化ペイロード量、キーフレーム量、再送を含む送受信統計、ネットワーク全体の通信量。
- 入力から表示までの遅延の中央値と上位分位、全体同期と映像復旧の時間。
- キャプチャ、差分検出、圧縮、送信待ち、デコード、描画にかかる時間。
- ホストのCPU・GPU・メモリ、送信待ち量、スマホ側の負荷。
- 変更領域の面積比、タイル数、パッチ数、更新の集約数、フレーム破棄数。
- DirtyRegionsの矩形数、重複を除いた面積比、全画面更新の割合、無更新の頻度、画素比較による追加の絞り込み効果。

数値目標は段階1の基準測定後に決める。静止中の画面データ送信停止、表示の正しさ、既存操作の維持、送信待ち量の有界性は差分方式の必須条件とする。通信量だけを採用判断に使わない。

各段階の結果を記録し、効果が確認できない追加最適化は次段階へ持ち込まない。従来VP8方式へ戻せる状態でWindowsとスマホの実機検証を行う。
